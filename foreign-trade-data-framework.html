外贸后台数据补充体系
底层框架 · 家族化数据集 · 场景全展开

本文从最底层的数据元模型出发，逐步构建起外贸后台"全场景数据补充"的完整知识框架。 我们不仅讲"怎么做"，更重要的是讲为什么这样设计——每一层抽象、每一个算子、 每一条数据血缘，都基于外贸业务本身的底层逻辑。

📚 阅读路线
如果你是完全的新手，建议从 第 1 章 开始顺序阅读； 如果你已有基础，可以直接跳到 第 2 章 框架部分； 想看具体场景实现，请移步 第 4 章。

一、外贸数据底层元模型

所有数据补充的前提，是我们对"数据"本身有一个精确的、可操作的定义。 在分布式系统与业务建模的交汇处，我们采用三元组元模型作为一切的起点。

1.1 实体 · 属性 · 关系 —— 数据的三原色

任何外贸业务数据都可以拆解为三个不可再分的基本要素：

● 实体 (Entity)
业务世界中可被唯一标识的"事物"。一个客户、一个产品、一个订单、一个集装箱……每个实体有一个 entity_id 和 entity_type。
● 属性 (Attribute)
实体在某一个维度上的"取值"。例如客户的 company_name、订单的 total_amount。属性是数据补充的最小作用单元。
● 关系 (Relation)
两个实体之间具有业务语义的"连线"。Customer -(places)→ Order、Order -(contains)→ Product。关系是数据集"家族化"的骨架。

用数学语言表达：

// 外贸数据宇宙 D 是一个三元组
D = (E, A, R)

E = { e₁, e₂, ..., eₙ }                    // 实体集合
A = { (e, k, v) | e ∈ E, k ∈ Key, v ∈ Val } // 属性集合
R = { (eᵢ, rⱼ, eₖ) | eᵢ, eₖ ∈ E }          // 关系集合

// 数据补充就是：对指定的 (e, k) 计算出 v
supplement(e, k) → v
📄 为什么从这里开始？
因为任何数据补充操作，本质上都是在回答"某个实体在某个属性上的值应该是什么"。 不理解这个最基本的问题，就不可能设计出通用的补充框架。所有后续的复杂度——场景、规则、引擎——都是在这个元模型上叠加的。

1.3 关系代数 —— 家族关系的数学表达

实体之间的关系不是任意的。外贸业务中存在 7 种基本关系类型，它们构成了所有数据血缘的"字母表"：

关系类型符号语义示例
拥有e₁ →has→ e₂e₁ 拥有 e₂Customer →has→ Contract
属于e₁ →belongs→ e₂e₁ 属于 e₂OrderItem →belongs→ Order
引用e₁ →refs→ e₂e₁ 引用 e₂Order →refs→ Customer
产生e₁ →produces→ e₂e₁ 产生 e₂Order →produces→ Invoice
依赖e₁ →depends→ e₂e₁ 依赖 e₂Shipment →depends→ Order
等价e₁ ≡ e₂e₁ 与 e₂ 是同一事物Product.SKU ≡ OrderItem.SKU
派生e₁ ↦ e₂e₂ 由 e₁ 计算得出OrderItem ↦ Invoice.amount

用关系图表达核心实体之间的联系：

[Customer] ──refs──→ [Order] ──produces──→ [Invoice] | | | has | contains ↓ ↓ [Contract] [OrderItem] ──refs──→ [Product] | | depends ↓ [Shipment] ──has──→ [Container] [Payment] ──refs──→ [Invoice] [FxRate] ──refs──→ [Payment] [Inventory] ──refs──→ [Product], [Warehouse]
⚙ 关系作为"路径"
从元模型角度看，数据补充的本质是"沿着关系路径在实体之间传播信息"。 例如，要补充 Invoice.amount，可以沿着 Invoice ←produces— Order —contains→ OrderItem 这条路径， 从 OrderItem.qty × OrderItem.unit_price 推导出来。 这就是"数据补充"的底层机制——关系路径传播。

二、数据补充框架 —— 分层架构与算子体系

有了元模型和关系代数，我们可以设计一个通用的数据补充框架。 这个框架分为 5 层，每一层解决一个特定的抽象级别。

2.1 五层架构

┌─────────────────────────────────────────────────────┐ │ L5 业务场景层 (场景编排器) │ │ 客户管理 · 订单交易 · 供应链 · 财务 · 数据分析 │ └───────────────────────┬─────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────────┐ │ L4 数据补充规则层 (规则引擎) │ │ 推导规则 · 映射规则 · 聚合规则 · 校验规则 │ └───────────────────────┬─────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────────┐ │ L3 补充算子层 (原子操作) │ │ Lookup · Compute · Derive · Merge · Fill · Validate│ └───────────────────────┬─────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────────┐ │ L2 关系传播层 (图引擎) │ │ 路径搜索 · 关系遍历 · 血缘追踪 · 依赖解析 │ └───────────────────────┬─────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────────┐ │ L1 数据存储层 (元模型实现) │ │ 实体仓库 · 属性索引 · 关系图库 · 快照版本 │ └─────────────────────────────────────────────────────┘

各层职责：

层级核心能力输入/输出
L1 数据存储以 (entity, attribute, value) 三元组存储所有数据；支持时间维度的快照CRUD + 时间旅行查询
L2 关系传播在关系图中搜索"补充路径"；解析依赖拓扑；计算可达性实体 → 可达实体集合 + 路径
L3 补充算子6 种原子操作：Lookup（查表）、Compute（计算）、Derive（推导）、Merge（合并）、Fill（填充默认值）、Validate（校验）(e, k) → 补充后的 v
L4 规则层将业务规则表达为"触发条件 × 算子序列"；管理规则的优先级、冲突、覆盖场景需求 → 可执行的规则链
L5 场景层接收业务场景的"补充请求"，编排 L4 规则，返回完整的补充结果场景 + 参数 → 补充后的数据集

2.2 六种补充算子详解

算子是框架的最小执行单元。每个算子接收一个"补充上下文" Ctx = (entity, attribute, existing_value, graph)，输出补充后的值。

① Lookup（查表）
从外部参考表或编码表中查找值。如：根据 currency_code 查 currency_name、根据 HS code 查产品类别。
② Compute（计算）
基于算术/逻辑表达式计算。如：total_amount = ∑(qty × unit_price)、net_weight = gross_weight × (1 - tare_rate)。
③ Derive（推导）
沿关系路径从关联实体推导。如：从 Customer.region 推导 Order.export_region。
④ Merge（合并）
将多个来源的值合并为单一值。如：合并多个 Supplier.quote 取最低价。
⑤ Fill（填充）
当无数据可用时，填入合理的默认值或生成值。如：填充 created_at = now()、status = 'draft'。
⑥ Validate（校验）
检查补充结果是否满足约束。如：金额必须 > 0、日期必须 < 当前日期 + 90 天。不满足时触发"二次补充"。

2.3 数据质量合约

框架内置了一套数据质量合约，在补充之前、之中、之后都有明确的约束：

// 数据质量合约 (Data Quality Contract)
interface QualityContract {
  // 补充前：缺失度检查
  completeness: (entity, attribute) → number   // 0.0 ~ 1.0

  // 补充中：一致性约束
  consistency: (entity, attribute, value) → boolean

  // 补充后：准确性验证
  accuracy: (entity, attribute, value) → Verdict

  // 时效性：数据新鲜度
  freshness: (entity, attribute) → Duration

  // 可追溯：数据来源记录
  provenance: ProvenanceRecord
}

// 完整性等级
enum CompletenessLevel {
  CRITICAL,        // 必须 100% 补充
  HIGH,            // 补充到 ≥95%
  MEDIUM,          // 补充到 ≥80%
  LOW,             // 补充到 ≥60%
  BEST_EFFORT      // 尽力补充，不强制
}

三、家族化数据集 —— 从"数据"到"数据家族"

"家族化"是本文的核心概念。传统的数据集是一个个孤立的表，而家族化数据集 模拟真实外贸世界中实体之间的"家庭关系"——一个客户和它的合同、订单、发票、收款记录之间， 有类似于"父母-子女-孙辈"的血缘关系。

3.1 家族树设计

每个实体类型在家族树中有一个"辈分"：

辈分含义实体类型
ROOT根节点，独立存在Customer, Supplier, Product, User
PARENT包含子节点Order, Contract, Shipment
CHILD属于父节点OrderItem, Invoice, Payment, Container
LEAF叶子节点，无子节点ComplianceDoc, FxRate, Inventory

一个完整的数据家族由同一条业务主线的所有相关实体组成：

┌───────────────────────────────────────────────────────────┐ │ 家族: Customer #1001 │ │ (Root / Party) │ ├───────────────────────────────────────────────────────────┤ │ │ │ ┌─ Contract #C2024-001 (Parent/Legal) ──┐ │ │ │ ├─ ComplianceDoc #DOC-A (Leaf) │ │ │ │ └─ ComplianceDoc #DOC-B (Leaf) │ │ │ └────────────────────────────────────────┘ │ │ │ │ ┌─ Order #ORD-2024-0001 (Parent/Transaction) ──────────┐│ │ │ ├─ OrderItem #1 (Child) ──→ Product #SKU-001 ││ │ │ ├─ OrderItem #2 (Child) ──→ Product #SKU-002 ││ │ │ ├─ Invoice #INV-001 (Child/Finance) ││ │ │ │ └─ Payment #PAY-001 (Leaf) ││ │ │ └─ Shipment #SHP-001 (Child/Logistics) ││ │ │ └─ Container #CONT-001 (Leaf) ││ │ └──────────────────────────────────────────────────────┘│ │ │ │ ┌─ Order #ORD-2024-0002 (Parent) ──────────────────────┐│ │ │ ├─ OrderItem #3 ──→ Product #SKU-001 ││ │ │ └─ Invoice #INV-002 ──→ Payment #PAY-002 ││ │ └──────────────────────────────────────────────────────┘│ └───────────────────────────────────────────────────────────┘
🔥 家族化的价值
家族化数据集的三大优势：因果一致性（同一家族的数据遵循相同的业务逻辑）、 传播完整性（数据补充可以沿家族树传播）、模拟逼真度 （模拟数据生成时，家族内部的数据分布自然协调，不会出现"客户的订单金额超过其信用额度"这样的矛盾）。

3.2 模拟生成引擎 —— 家族数据工厂

模拟生成引擎的核心是一个家族生成器：

// 家族生成器伪代码
class FamilyGenerator {

  // 种子参数：控制家族的数量和规模分布
  __init__(seed_params):
    self.num_customers = seed_params.num_customers          // 客户数量
    self.orders_per_customer = seed_params.orders_per_customer // 分布参数
    self.items_per_order = seed_params.items_per_order
    self.product_pool_size = seed_params.product_pool_size
    self.rng = Random(seed_params.seed)                       // 可复现随机

  // 生成完整的家族数据集
  def generate():
    products = self._generate_product_pool()
    customers = []
    for i in range(self.num_customers):
      customer = self._generate_customer(i)
      orders = []
      num_orders = self.rng.poisson(self.orders_per_customer)
      for j in range(num_orders):
        order = self._generate_order(customer, j)
        items = []
        num_items = self.rng.uniform(1, self.items_per_order)
        for k in range(num_items):
          item = self._generate_order_item(order, products[k])
          items.append(item)
        order.items = items
        order.total_amount = sum(item.qty * item.unit_price for item in items)
        // 沿家族树传播：订单 → 发票 → 付款
        invoice = self._generate_invoice(order)
        payment = self._generate_payment(invoice)
        // 物流分支
        shipment = self._generate_shipment(order)
        container = self._generate_container(shipment)
        orders.append(order)
      customer.orders = orders
      customers.append(customer)
    return { customers, products }
}

数据分布策略 —— 让数据"像真的"

家族化数据集的关键在于层叠式分布约束：

层级分布策略模拟示例
客户层地域分布按真实外贸比例（EU 30%, NA 25%, APAC 20%, ...）region = weighted_choice(['EU','NA','APAC','ME','LATAM','AFRICA'], weights)
订单层订单金额满足幂律分布（帕累托80/20）amount = pareto(alpha=1.5) * scale_factor
产品层产品类别嵌套，HS Code 按真实贸易占比hs_code = random_choice(top_100_hs_codes)
时间层订单日期有季节性波动和周末效应date = seasonal_baseline + weekly_noise
货币层汇率序列带均值回归特性rate = previous_rate + mean_reversion + noise

3.3 数据血缘与版本管理

家族化数据集必须记录数据血缘——每个数据值"从哪里来"：

// 血缘记录 (ProvenanceRecord)
{
  "entity_id":    "ORD-2024-0001",
  "attribute":    "total_amount",
  "value":        12500.00,
  "provenance": [
    {
      "source":     "OrderItem",
      "operator":   "Compute",
      "rule":       "total_amount = sum(qty * unit_price)",
      "inputs":     ["item_1.amount", "item_2.amount"],
      "timestamp":  "2024-06-15T10:30:00Z"
    },
    {
      "source":     "FxRate",
      "operator":   "Lookup",
      "rule":       "convert to USD using rate on order_date",
      "inputs":     ["FX_2024-06-15_USD_CNY"],
      "timestamp":  "2024-06-15T10:30:01Z"
    }
  ],
  "version": 2,           // 数据版本号
  "valid_from": "2024-06-15",  // 生效时间
  "valid_to":   "2024-06-20"    // 失效时间 (快照版本)
}

四、场景全展开 —— 六大核心场景的数据补充

本章将上述框架映射到 6 个核心外贸场景。每个场景我们回答三个问题：

  1. 补充什么？ —— 该场景下需要补充的实体和属性
  2. 从哪补充？ —— 数据来源和关系路径
  3. 怎么补充？ —— 使用的算子链和规则

4.1 客户管理场景

场景描述： 外贸企业需要构建完整的客户画像，包括基础信息、信用等级、交易历史、偏好分析等。数据补充的目标是让每个客户从"一个名字"变成"一个完整的档案"。

补充属性缺失场景补充算子数据来源/关系路径
Customer.credit_level新客户注册时无信用评级Lookup + Compute查外部信用库 + 根据注册资本/年限计算
Customer.region只有国家代码，无区域分组Lookupcountry_code → region 映射表
Customer.avg_order_value新客户无历史数据Derive同类客户（同 region + tier）的均值
Customer.preferred_currency未设置偏好货币Derive从历史订单中提取最常用货币
Customer.last_contact_dateCRM 记录不完整Merge合并 Order.date + Email.date + Call.date
Customer.risk_flag合规风控数据缺失Compute基于 credit_level + payment_delay + region 计算
// 客户信用等级补充规则示例
rule "客户信用等级补充":
  trigger: Customer.credit_level is NULL
  priority: HIGH
  steps:
    // 第一步：尝试从外部信用库查询
    - Lookup(source="external_credit_db", key=Customer.reg_number)
    // 第二步：如果查不到，基于注册资本计算
    - if result is NULL:
        Compute(
          expression: "base_score = min(reg_capital / 1000000 * 10, 100)",
          adjustment: "years_in_business * 2",
          output: "credit_level (A/B/C/D)"
        )
    // 第三步：校验结果必须在有效范围内
    - Validate(condition: credit_level in ['AAA', 'AA', 'A', 'B', 'C', 'D'])

4.2 产品管理场景

场景描述： 产品数据是外贸业务的核心基准数据。补充的重点是产品分类标准化、属性完整化、HS Code 合规化。

补充属性缺失场景补充算子数据来源/关系路径
Product.hs_code产品无 HS Code 或只有 6 位Lookup + Derive根据产品名称/描述匹配 HS Code 数据库
Product.category_path只有叶子分类Lookup从分类树补齐完整路径
Product.unit_weight未录入重量Derive + Fill从同类产品推导或填入行业均值
Product.origin_country原产国缺失Derive从 Supplier.country 沿关系传播
Product.tax_rate出口退税率缺失Lookuphs_code → tax_rate 税务数据库
Product.min_order_qtyMOQ 未设置Fill按产品类别填入默认值
// HS Code 自动补充算法
def supplement_hs_code(product):
    // 1. 精确匹配：产品名称
    code = hs_code_db.exact_match(product.name_en)
    if code: return code

    // 2. 模糊匹配：关键词提取
    keywords = extract_keywords(product.description)
    candidates = hs_code_db.search_by_keywords(keywords)
    if candidates:
        return rank_and_select(candidates, "confidence > 0.85")

    // 3. 家族推导：从同类产品继承
    sibling = find_sibling_product(product.category_id)
    if sibling:
        return sibling.hs_code

    // 4. 兜底：填入大类码
    return category_to_hs_prefix(product.category_id) + "000000"

4.3 订单交易场景

场景描述： 订单是外贸业务的核心交易载体。数据补充的目标是确保订单的完整性、可计算性和可追溯性。

补充属性缺失场景补充算子数据来源/关系路径
Order.total_amount未汇总Compute∑(OrderItem.qty × OrderItem.unit_price)
Order.currency货币未指定Derive从 Customer.preferred_currency 继承
Order.incoterm贸易术语缺失Derive + Fill从 Contract 继承，或填入默认 FOB
Order.export_declaration_no报关单号未回填Lookup从海关对接系统查询
OrderItem.hs_code行项 HS Code 缺失Derive从 Product.hs_code 沿 refs 关系传播
OrderItem.estimated_weight预估重量ComputeProduct.unit_weight × qty
// 订单金额补充 + 多重校验
rule "订单金额全链路补充":
  steps:
    // 1. 计算行项金额
    - for each OrderItem in Order.items:
        item.amount = Compute(qty * unit_price * (1 - discount_rate))

    // 2. 汇总订单金额
    - Order.subtotal = Compute(sum(item.amount for item in items))

    // 3. 补充运费和保险费
    - Order.freight = Derive(
        from: Shipment,
        using: "feight = total_weight * rate_per_kg"
      )
    - Order.insurance = Compute(subtotal * 0.001)  // 千分之一

    // 4. 最终金额
    - Order.total_amount = Compute(subtotal + freight + insurance)

    // 5. 校验：金额一致性
    - Validate(
        condition: abs(total_amount - sum(item.amount) - freight - insurance) < 0.01,
        on_fail: "trigger_reconciliation"
      )

// 供应链 ETA 预测与补充
def supplement_eta(shipment, route_db):
    route = route_db.get_route(
        origin = shipment.origin_port,
        destination = shipment.destination_port,
        carrier = shipment.carrier_code
    )
    if not route:
        // 尝试用历史数据推导
        route = historical_avg(shipment.origin_port, shipment.destination_port)

    base_transit = route.base_days
    // 季节性调整
    seasonal_factor = get_seasonal_factor(shipment.etd.month, route)
    // 港口拥堵调整
    congestion = get_port_congestion(shipment.destination_port)

    eta = shipment.etd + timedelta(
        days = base_transit * seasonal_factor + congestion
    )
    return eta

// 汇率链式补充 (处理多币种)
def fx_chain_supplement(invoice, fx_table):
    // 目标：所有金额统一为 USD
    if invoice.currency == "USD":
        return invoice.amount

    // 直接汇率：invoice.currency → USD
    rate = fx_table.get_rate(invoice.currency, "USD", invoice.date)
    if rate:
        return invoice.amount * rate

    // 链式汇率：invoice.currency → EUR → USD
    // 或 invoice.currency → CNY → USD
    for intermediate in ["EUR", "CNY", "GBP", "JPY"]:
        rate1 = fx_table.get_rate(invoice.currency, intermediate, invoice.date)
        rate2 = fx_table.get_rate(intermediate, "USD", invoice.date)
        if rate1 and rate2:
            return invoice.amount * rate1 * rate2

    // 兜底：使用最近可用汇率
    rate = fx_table.nearest_rate(invoice.currency, "USD", invoice.date)
    if rate:
        return invoice.amount * rate

    raise SupplementError("无法补充汇率")

// 客户生命周期价值 (LTV) 补充
def supplement_ltv(customer, all_orders, all_payments):
    // 1. 收集该客户的所有订单
    customer_orders = [o for o in all_orders if o.customer_id == customer.id]

    // 2. 计算总收入
    total_revenue = sum(o.total_amount for o in customer_orders)

    // 3. 计算退货金额
    total_refunds = sum(
        p.amount for p in all_payments
        if p.order_id in [o.id for o in customer_orders]
        and p.type == "refund"
    )

    // 4. 计算客户时长 (年)
    first_order_date = min(o.order_date for o in customer_orders)
    tenure_years = (today - first_order_date).days / 365.0

    // 5. LTV = (总收入 - 总退款) / 年限
    ltv = (total_revenue - total_refunds) / max(tenure_years, 0.5)

    // 6. 校验：LTV 不能为负
    return max(ltv, 0)

// ============================================================
// 外贸家族化数据集模拟生成器 (Python 伪代码)
// ============================================================
import random
import datetime
from dataclasses import dataclass
from typing import List, Optional

// ─── 基础类型 ───
@dataclass
class Entity:
    entity_id: str
    entity_type: str
    attributes: dict

@dataclass
class Relationship:
    source_id: str
    target_id: str
    rel_type: str   // "has" | "belongs" | "refs" | ...

// ─── 种子参数 ───
@dataclass
class SeedParams:
    num_customers: int = 50
    orders_per_customer: tuple = (1, 8)   // (min, max)
    items_per_order: tuple = (1, 5)
    product_pool: int = 100
    date_start: str = "2023-01-01"
    date_end: str = "2024-12-31"
    seed: int = 42
    currency_dist: dict = None  // 如 {"USD": 0.6, "EUR": 0.2, "CNY": 0.1, ...}
    incoterm_dist: dict = None

// ─── 家族生成器 ───
class FamilyDataGenerator:
    def __init__(self, params: SeedParams):
        self.p = params
        self.rng = random.Random(params.seed)
        self.entities: [Entity] = []
        self.relationships: [Relationship] = []
        self._init_distributions()

    def _init_distributions(self):
        // 地域分布 (真实外贸比例)
        self.regions = ["EU", "NA", "APAC", "ME", "LATAM", "AFRICA"]
        self.region_weights = [0.30, 0.25, 0.20, 0.10, 0.10, 0.05]

        // 货币分布
        self.currencies = self.p.currency_dist or {
            "USD": 0.55, "EUR": 0.20, "CNY": 0.10,
            "GBP": 0.05, "JPY": 0.05, "AUD": 0.03, "其他": 0.02
        }

        // 产品类别 (HS 2 位)
        self.hs_categories = {
            "84": "机械器具",  "85": "电气设备",
            "61": "针织服装",  "62": "非针织服装",
            "73": "钢铁制品",  "39": "塑料制品",
            "94": "家具",      "64": "鞋类",
            "90": "光学仪器",  "95": "玩具"
        }

    def _weighted_choice(self, items, weights):
        return self.rng.choices(items, weights=weights, k=1)[0]

    def _random_date(self):
        start = datetime.date(2023, 1, 1)
        end = datetime.date(2024, 12, 31)
        delta = (end - start).days
        return start + datetime.timedelta(days=self.rng.randint(0, delta))

    // ── 生成产品池 ──
    def generate_product_pool(self) -> List[Entity]:
        products = []
        for i in range(self.p.product_pool):
            hs2 = self.rng.choice(list(self.hs_categories.keys()))
            unit_price = round(self.rng.lognormvariate(3.5, 0.8), 2)
            weight = round(self.rng.lognormvariate(2.0, 1.0), 1)
            products.append(Entity(
                entity_id = f"SKU-{i+1:04d}",
                entity_type = "Product",
                attributes = {
                    "name": f"Product_{i+1}",
                    "hs_code": f"{hs2}0{i%100:04d}",
                    "category": self.hs_categories[hs2],
                    "unit_price": unit_price,
                    "unit_weight": weight,
                    "origin_country": self._weighted_choice(
                        ["CN", "VN", "IN", "KR", "DE", "US"],
                        [0.60, 0.12, 0.10, 0.08, 0.06, 0.04]
                    )
                }
            ))
        self.entities.extend(products)
        return products

    // ── 生成客户 + 完整家族 ──
    def generate_customer_family(self, idx: int, products: List[Entity]):
        // 1. 客户实体
        region = self._weighted_choice(self.regions, self.region_weights)
        credit_tier = self.rng.choices(
            ["AAA", "AA", "A", "B", "C", "D"],
            weights=[0.05, 0.15, 0.30, 0.30, 0.15, 0.05],
            k=1
        )[0]
        customer = Entity(
            entity_id = f"CUST-{idx+1:04d}",
            entity_type = "Customer",
            attributes = {
                "name": f"Customer_{idx+1}",
                "region": region,
                "credit_level": credit_tier,
                "preferred_currency": self._weighted_choice(
                    list(self.currencies.keys()),
                    list(self.currencies.values())
                ),
                "reg_capital": round(self.rng.lognormvariate(12, 1.5), 2)
            }
        )
        self.entities.append(customer)

        // 2. 合同 (可选)
        if self.rng.random() < 0.7:
            contract = Entity(
                entity_id = f"CTR-{idx+1:04d}",
                entity_type = "Contract",
                attributes = {
                    "contract_no": f"CT{2024}{idx+1:04d}",
                    "valid_from": "2024-01-01",
                    "valid_to": "2024-12-31",
                    "terms": "CIF"
                }
            )
            self.entities.append(contract)
            self.relationships.append(Relationship(
                customer.entity_id, contract.entity_id, "has"))

        // 3. 订单 (家族核心)
        num_orders = self.rng.randint(self.p.orders_per_customer[0],
                                          self.p.orders_per_customer[1])
        for j in range(num_orders):
            order_date = self._random_date()
            currency = customer.attributes["preferred_currency"]
            incoterm = self.rng.choice(["FOB", "CIF", "EXW", "DDP", "FCA"])

            order = Entity(
                entity_id = f"ORD-{idx+1:04d}-{j+1:04d}",
                entity_type = "Order",
                attributes = {
                    "order_date": order_date.isoformat(),
                    "currency": currency,
                    "incoterm": incoterm,
                    "status": self.rng.choice(
                        ["confirmed", "shipped", "delivered", "closed"],
                        weights=[0.1, 0.2, 0.4, 0.3]
                    )
                }
            )
            self.entities.append(order)
            self.relationships.append(Relationship(
                customer.entity_id, order.entity_id, "refs"))

            // 3a. 订单行项
            num_items = self.rng.randint(self.p.items_per_order[0],
                                        self.p.items_per_order[1])
            item_total = 0
            selected = self.rng.sample(products, min(num_items, len(products)))
            for k, prod in enumerate(selected):
                qty = self.rng.randint(10, 1000)
                price = prod.attributes["unit_price"]
                amount = round(qty * price, 2)
                item_total += amount
                item = Entity(
                    entity_id = f"OI-{idx+1:04d}-{j+1:04d}-{k+1:04d}",
                    entity_type = "OrderItem",
                    attributes = {
                        "qty": qty,
                        "unit_price": price,
                        "amount": amount,
                        "delivery_date": (order_date + datetime.timedelta(
                            days=self.rng.randint(15, 60))).isoformat()
                    }
                )
                self.entities.append(item)
                self.relationships.append(Relationship(
                    order.entity_id, item.entity_id, "belongs"))
                self.relationships.append(Relationship(
                    item.entity_id, prod.entity_id, "refs"))

            // 补全订单总金额
            order.attributes["total_amount"] = round(item_total, 2)

            // 3b. 发票 (家族传播)
            invoice = Entity(
                entity_id = f"INV-{idx+1:04d}-{j+1:04d}",
                entity_type = "Invoice",
                attributes = {
                    "amount": order.attributes["total_amount"],
                    "currency": currency,
                    "tax_rate": round(self.rng.uniform(0, 0.13), 4),
                    "due_date": (order_date + datetime.timedelta(
                        days=self.rng.randint(30, 90))).isoformat()
                }
            )
            self.entities.append(invoice)
            self.relationships.append(Relationship(
                order.entity_id, invoice.entity_id, "produces"))

            // 3c. 付款 (可选)
            if self.rng.random() < 0.85:
                payment = Entity(
                    entity_id = f"PAY-{idx+1:04d}-{j+1:04d}",
                    entity_type = "Payment",
                    attributes = {
                        "amount": invoice.attributes["amount"],
                        "method": self.rng.choice(
                            ["T/T", "L/C", "D/P", "D/A"],
                            weights=[0.5, 0.3, 0.15, 0.05]
                        ),
                        "payment_date": (order_date + datetime.timedelta(
                            days=self.rng.randint(10, 60))).isoformat()
                    }
                )
                self.entities.append(payment)
                self.relationships.append(Relationship(
                    invoice.entity_id, payment.entity_id, "refs"))

            // 3d. 发货 (可选)
            if self.rng.random() < 0.9:
                shipment = Entity(
                    entity_id = f"SHP-{idx+1:04d}-{j+1:04d}",
                    entity_type = "Shipment",
                    attributes = {
                        "carrier": self.rng.choice(
                            ["COSCO", "MSC", "MAERSK", "CMA-CGM", "EVERGREEN"]),
                        "etd": (order_date + datetime.timedelta(
                            days=self.rng.randint(5, 20))).isoformat(),
                        "eta": (order_date + datetime.timedelta(
                            days=self.rng.randint(25, 50))).isoformat()
                    }
                )
                self.entities.append(shipment)
                self.relationships.append(Relationship(
                    order.entity_id, shipment.entity_id, "depends"))

    // ── 入口：生成完整家族数据集 ──
    def generate(self) -> FamilyDataset:
        print(f"生成 {self.p.num_customers} 个客户家族...")
        products = self.generate_product_pool()
        print(f"  产品池: {len(products)} 个 SKU")
        for i in range(self.p.num_customers):
            self.generate_customer_family(i, products)
        print(f"生成完成: {len(self.entities)} 实体, {len(self.relationships)} 关系")
        return FamilyDataset(self.entities, self.relationships)

7.1 多平台运营模型

平台数据的补充策略：

● 佣金计算
Lookup 算子从平台费率表获取基础佣金率，再通过 Compute 算子按品类/金额阶梯计算实际佣金。
● 流量转化
Compute 算子计算 转化率 = 订单数 / 访客数、客单价 = 营收 / 订单数。不同平台维度聚合。
● 跨平台归一化
Derive 算子将各平台的订单状态、退款流程、物流编码映射到统一的内部状态模型。
● 平台费用预测
Merge 算子合并历史费用数据，Compute 算子预测未来平台成本。

// ROI 指标计算（所有算子自动执行）

// 1. ROAS (Return on Ad Spend) = 归因营收 / 广告花费
campaign.roas = Compute(
  attributed_revenue / total_spend,
  output: "x 倍"
)

// 2. CAC (Customer Acquisition Cost) = 总花费 / 新增客户数
campaign.cac = Compute(
  total_spend / new_customers,
  output: "$/客户"
)

// 3. CPA (Cost Per Acquisition) = 总花费 / 订单数
campaign.cpa = Compute(
  total_spend / total_orders,
  output: "$/订单"
)

// 4. LTV : CAC 比率 = 客户生命周期价值 / 获客成本
campaign.ltv_cac_ratio = Compute(
  customer_ltv / cac,
  output: "x 倍"
)

// 5. 归因营收（Merge 算子：多触点归因）
campaign.attributed_revenue = Merge(
  sources: [
    "last_click_orders.total",
    "first_click_orders.total",
    "linear_attribution_orders.total"
  ],
  strategy: "last_click_weighted"
)

[Platform] ←── [Campaign] ──refs──→ [ProductCategory] | | | has | part_of ↓ ↓ [PlatformListing] ──refs──→ [Product] ──belongs──→ [Category (2位)] | | refs ↓ [Customer] ──refs──→ [Order] ──comes_from──→ [Platform] | | | has | attributed_to ↓ ↓ [Contract] [Campaign] // 新增关系类型 comes_from: Order → Platform // 订单来自哪个平台 attributed_to: Order → Campaign // 订单归因于哪个营销活动 runs_on: Campaign → Platform // 活动在哪个平台投放 promotes: Campaign → Category // 活动推广哪个品类
🔥 扩展框架的核心原则
归一化： 无论增加多少平台、渠道、品类，底层的元模型不变——实体、属性、关系。 6 种补充算子不变——Lookup / Compute / Derive / Merge / Fill / Validate。 区别只在于：关系路径更多了，数据来源更丰富了，补充规则更智能了。

这就是"底层框架"的真正价值——它不是为某个场景定制的，而是能够容纳所有场景的通用数据补全基础设施。
📚 总结
从底层到应用，整个体系只用了一个核心思想：

数据补充 = 沿着关系路径传播信息

元模型定义了"信息"是什么（实体-属性-值），关系代数定义了"路径"有哪些， 框架定义了"传播"如何执行（6 种算子），家族化数据集确保"传播"的结果是自洽的， 场景层则告诉框架"传播到哪"。

这就是外贸后台数据补充的全部秘密——从最底层开始，一层一层搭建起来，每一层都建立在前一层的基础上， 最终形成一个完整的、可用于任何场景的数据补充体系。
